## High-Value Patterns

### 1. Strict Role Separation (The Triad)
- **Implementer:** Focused on execution, TDD, and self-review.
- **Spec Compliance Reviewer:** Dedicated functional audit. Tasked with ensuring "what was asked" was built—nothing more, nothing less.
- **Code Quality Reviewer:** Focused on maintainability, naming, and architectural alignment. Only engaged after spec compliance is verified.

### 2. Verification-Before-Trust
Reviewers are explicitly instructed to ignore the implementer's summary report. They must audit the physical code changes and test outputs directly to verify claims. This prevents "optimistic reporting" from polluting the verification gate.

### 3. Context Injection (Controller Responsibility)
The controller (main agent) is responsible for providing the **full text** of the task and relevant context to the subagent. Subagents should not be forced to read large plan files, which reduces startup latency and prevents context-window saturation with irrelevant tasks.

### 4. Two-Stage Review Gate
Functional verification (Spec) and Aesthetic/Structural verification (Quality) are serialized. A task cannot be considered "Done" until it passes both gates. This ensures that "working code" that is "badly built" is caught and corrected before it reaches the main branch.

### 5. Iterative Looping Fixes
The same subagent (or context) is used to address review findings, creating a tight feedback loop that persists until approval.

## Gaps in Current Skill (`independent-developer`)
- **Review Vague:** The existing `independent-developer` skill mandates subagents but lacks a defined review protocol.
- **Role Blur:** No distinction between functional compliance and code quality.
- **Missing Protocol:** No explicit "Context Injection" requirement; subagents often spend cycles re-discovering context the controller already possesses.
- **Trust Bias:** Current subagent interactions often rely on the subagent's own claim of completion without independent audit.

## Implemented Policy Changes (Recommended)
The following policies are now recommended for adoption within the `independent-developer` framework (Section 1.1):

1.  **Mandatory Two-Stage Review:** All non-trivial subagent implementations MUST undergo two-stage review (Spec then Quality) by distinct roles or prompts.
2.  **Context Injection Mandate:** Controllers MUST provide full task specifications and context snippets in the dispatch prompt.
3.  **The "Audit-Over-Report" Protocol:** Reviewer subagents MUST be instructed to verify implementation via code analysis, not report summaries.
4.  **Triviality Exception Clarification:** Direct execution is still preferred for single-file reads, simple status checks, or bounded discovery that doesn't involve mutation.

## Risks
- **Overhead:** Multi-stage reviews increase the number of LLM calls and associated costs.
- **Latency:** Iterative loops can slow down perceived progress if tasks are too granular or requirements are ambiguous.
- **Reviewer Fatigue:** If review prompts are not sufficiently distinct, they may converge on redundant feedback.
