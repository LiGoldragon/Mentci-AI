## 1. Why extend `Components/mentci-vcs`
`Components/mentci-vcs` already acts as the repository’s Rust-native VCS surface. `Components/index.edn` declares it as the writable lane orchestration component that implements `rust.vcs.wrapper`, and `/home/li/git/Mentci-AI--dev/Components/mentci-vcs/src/lib.rs` already centralizes the `jj` trait, environment sanitization, and the few CLI commands the agents currently trust. Building a second component would duplicate the configuration, policy gating, and the zero-interaction invocation boilerplate that this crate already provides, violating the single-source-of-trust philosophy the repository enforces for `dev`/`main` lanes (see `/home/li/git/Mentci-AI--dev/docs/plans/2026-03-11-jj-cleanup-training-and-sane-jj-plan.md`). Extending the existing component keeps the interface consistent for the tooling (e.g., `Components/nix/mentci_vcs.nix`, `Components/nix/common_packages.nix`) that already references `mentci-vcs` and preserves the test harness that already executes via `cargo test -p mentci-vcs`.

## 2. `jj-lib` vs shelling out to `jj`
The canonical `jj-lib` crate (https://docs.rs/jj-lib/latest/jj_lib/) exposes structured data models for commits, worktrees, bookmarks, and operations, but the published API surface is enormous: `absorb`, `commit_builder`, `diff_presentation`, `git_backend`, `workspace_store`, plus asynchronous dependencies such as `tokio`, `prost`, and `gix`. Bringing that dependency into `mentci-vcs` would force the component to compile and audit every layer of `jj`’s internal plumbing, while locking us to upstream release cadence and nightly changes in the `jj` repo. In contrast, the current `Components/mentci-vcs/src/lib.rs` already shells out to the stable `jj` CLI via `std::process::Command` with explicit environment overrides (`JJ_CONFIG`, `PAGER=cat`, `CI=true`), keeping compiled dependencies minimal and decoupling the wrapper from `jj`’s internal data structures. The best long-term hybrid is to keep the CLI invocation for day-to-day commands but wrap it with typed builders and structured JSON output; `jj-lib` can be reconsidered once a modular subset of its API stabilizes and the component can vendor it without dragging in the entire `jj` workspace (see `/home/li/git/Mentci-AI--dev/Research/high/Structural-Editing/591912110255_report_jujutsu_mcp_landscape.md` for a similar typed-vs-shell-out trade study).

## 3. Proposed command set for sane-JJ
1. `sane-preflight` – runs `jj status --json`, a bounded log over `${MENTCI_TARGET_BOOKMARK:-dev}|${MENTCI_TARGET_BOOKMARK:-dev}@origin|@|@-`, and bookmark inspection under the sanitized environment, emitting a JSON packet with change IDs, dirty files, and bookmark topology to drive downstream gates.
2. `sane-intent-start` – mirrors `jj new -m` with metadata, automatically annotating `intent: <task>` and `session: <token>` and emitting the resulting change ID so other agents can record it in the session ledger.
3. `sane-commit` – enforces `jj commit` with guard rails (no new working copy commits when the runtime bookmark is unresolved or when diffs show the commit is empty) and emits the resulting change ID plus pre/post evidence for policy review.
4. `sane-finalize` – groups the previous commands, performs preflight, then commits, pushes (if allowed), and captures the runtime bookmark update as structured JSON.
5. `sane-bookmark-move` – implements bookmark-safe moves, ensuring side bookmarks are classified (`protected`, `audit`, `cleanup`), only moving ones marked for mutation, and providing dry-run previews of the proposed target before touching refs.
6. `sane-push-verify` – fetches the remote runtime bookmark, computes bounded divergence against `${MENTCI_TARGET_BOOKMARK:-dev}`, and fails closed if local state would drop pending `@` beneath the runtime bookmark; returns JSON evidence so callers can decide if a rebase preview is required.
7. `sane-cleanup` – an explicit cleanup guard for removing noise `@` commits: it validates the range with `jj status --json`, ensures no described empty commits exist, then safely repositions the runtime target only when the working copy is empty.
8. `sane-rebase-preview` – orchestrates a bounded rebase preview from `${MENTCI_TARGET_BOOKMARK:-dev}` onto the intended integration bookmark plus `jj status --json`, so agents can inspect the effects before calling `sane-finalize`.

Each CLI subcommand will accept a `--json-output <path>` flag to persist the evidence packet and a `--preview` flag that runs the command against the projected invocation without mutating history.

## 4. Safety architecture
* **Typed command builder:** Define a Rust enum per `sane-` command, with strongly typed fields for bookmarks, change IDs, and boolean gates. The builder composes `Command` arguments via helper methods that escape values, set `JJ_CONFIG`, and annotate metadata (session, intent). This keeps quoting errors out of the safety-critical path.
* **Dry-run/preview modes:** Every command exposes `--preview` and `--dry-run` flags that execute the sequence of `jj` commands but exit before any mutation. The preview produces the same JSON evidence that the mutation path does so auditors can diff them before authorizing the real action.
* **JSON evidence packets:** Standardize emitted packets (timestamp, runtime bookmark, command parameters, command stdout/stderr, exit status, change IDs touched). Upstream agents (e.g., `mentci-policy-engine`, `mentci-launch`) will consume those packets to confirm the command adhered to policy before accepting the result.
* **Fail-closed rules:** If preflight evidence indicates pending merges, untracked files, or stale remote refs, the command exits non-zero and documents the reason in the JSON packet. Side-bookmark commands require explicit classification and cannot mutate bookmarks marked as `protected` or lacking explicit `--force`. This ensures `mentci-vcs` never transitions the runtime bookmark when the working copy is dirty or when `jj status --json` reports unresolved conflicts.

By tying this architecture directly to `Components/mentci-vcs`, the new surface stays aligned with the existing `rust.vcs.wrapper` interface the repo already trains on, and the JSON evidence packets plug cleanly into the future `mentci-policy-engine` verification layer described in the Task 1 roadmap.
